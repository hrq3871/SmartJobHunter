## 判断顺序

1. 先判断岗位本体 `role_family`：产品经理、产品运营、项目管理、解决方案、数据分析、前端工程、后端工程、算法研发、公关传播、品牌社媒、销售、客服、审核标注、纯运营或其他。
2. 再看核心职责是否匹配目标角色。标题和部门名只作为弱证据。
3. 再看目标领域是否真实进入职责或要求。AI/Agent/大模型只出现在标题、团队名或背景里，不等于 AI 产品岗。
4. 最后输出是否保留、分数、证据和 concerns。

## 高风险反例

以下岗位即使标题包含“AI”“产品”“大模型”，也通常不能当成 AI 产品经理：

- 公关传播、品牌传播、媒体关系、社媒、舆情、内容传播。
- 前端工程、Web 开发、组件库、Canvas、代码质量、工程效率。
- 后端、算法、研发、测试、运维等工程岗位。
- 销售、售前、客服、审核、标注、供应商管理、纯运营。

如果 profile 的目标角色不是这些方向，应拒绝或明显降权。

## 评分维度

- `core_role_fit`: 岗位真实角色是否符合目标岗位。
- `domain_fit`: 目标领域是否真实出现在职责/要求/产出中。
- `responsibility_fit`: 是否包含目标工作内容，例如需求分析、产品规划、用户/业务问题定义、落地推进、指标闭环。
- `preference_fit`: 地点、岗位性质、行业偏好是否一致。
- `risk_signals`: 是否存在非目标角色、标题党、纯执行、证据不足等风险。

`match_score` 反映证据强度，不按关键词数量打分。

- 0.8-1.0: 高度匹配，真实角色和核心职责都吻合。
- 0.6-0.8: 基本匹配，但存在少量缺口。
- 0.4-0.6: 部分相关，通常只作为候选复核。
- 0.0-0.4: 不匹配。

硬性规则：

- 标题单点命中只能算弱证据。
- 核心角色不匹配时，`match_score` 通常不应超过 0.45。
- 核心角色相邻但职责不闭环时，`match_score` 通常不应超过 0.65。
- 公关传播或前端工程类岗位，除非 profile 明确目标就是传播或工程，不得输出强保留。

```json
  "match_reasons": [],

  "concerns": [],
  "evidence": {
    "core_role": [],
    "domain": [],
    "responsibility": [],
    "risk_signals": []
  }

```

保留阈值：

- conservative: `match_score >= 0.8`
- moderate: `match_score >= 0.6`
- aggressive: `match_score >= 0.4`
